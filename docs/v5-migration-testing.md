# v5 migration in the development worktree

The implemented migration is being accepted on isolated fixtures and project copies. The installed v4 checkout, its services and real projects remain unchanged. A successful component test does not establish full v5 product acceptance.

Use the shared helper with the Council environment. `--check` is read-only for the target; `--plan` optionally saves a reviewable plan outside it. `--apply` requires that exact saved plan. A fresh plan uses a fresh filename, preventing accidental replacement of a reviewed plan.

```sh
council/.venv/bin/python skills/oppencouncil/scripts/oppencouncil.py upgrade-v5 /absolute/project-copy --check --plan /absolute/outside/project-copy-plan.json
council/.venv/bin/python skills/oppencouncil/scripts/oppencouncil.py upgrade-v5 /absolute/project-copy --apply --plan /absolute/outside/project-copy-plan.json
```

Select the actual installations with `--council-directory`, `--mcp-root` and, when necessary, `--mcp-config`. These options must match on check and apply. No service is started, restarted, registered or authorized by migration. Configured HTTP connections are probed at their loopback health endpoints; the Council probe uses its private admin credential without including it in reports. An old or unavailable registered service blocks application. An unregistered copy uses the new local Council package and does not require an optional MCP connection.

For stdio, the probe runs the selected installation in a fresh subprocess with its own interpreter and configuration. The report distinguishes this launch capability from a running HTTP listener and says when an existing client session needs reconnection. It does not claim that an already running stdio process has reloaded code. Reconnect the client to the upgraded installation before using the migrated project; existing OAuth grants and configuration are not changed.

The plan records the root, explicit/default project type, capabilities, input hashes, exact write paths and before/after hashes. Apply recomputes it under the original helper locks and the common project lock. Changed inputs or capabilities require a new check. Replaying the same successful plan is a no-op. `--project-type` is selected during check; later changes use the explicit project-type operation with a reason.

The migration retains the existing registry location, formal wording/version history, discussions, Memory bytes and Results registrations. It translates active Attention entries into investigations with original text and provenance. An unresolved investigation may remain open and blocking in v5: migration does not require resolving it, inventing an F, or changing the existing scientific rule. Its work blocker is distinct from the migration plan's capability/integrity blockers. A full project validation still reports unresolved blocking work; that is not evidence that the conversion failed. Legacy Markdown definitions, unnumbered scripts, problematic Results, unknown Data origins, Releases lacking manifests, experiments lacking status and unassigned files are reported for subsequent work. Migration does not repair those user artifacts or read archived experiment contents by default.

During application, `.oppencouncil-migration/` holds durable preimages on the same filesystem. A failure rolls back; a completed operation cleans up. Common helper, both legacy thin entry points and Council startup recover interrupted staging before reading authority. A conflicting later edit or corrupt preimage is reported without overwriting it. The explicit migration `--check` remains read-only and reports recovery needs instead of applying them.

Verification currently covers both native v3/v4 layouts, unchanged Memory and formal records, exact-plan replay/conflicts, post-write failures, real subprocess interruption and fresh Council startup recovery. `test_capabilities_v5.py` verifies old/current HTTP capability responses and CLI planning/application. Windows/Linux runs, real-project-copy migration, the full merged helper and the remaining v5 product features are separate acceptance items.

## Real project copies (2026-10-14)

Three real project copies were exercised without deploying v5 or modifying their original governance:

| Copy | Observed result |
| --- | --- |
| Steward v4 product project | 256 copied ordinary files and the original control-directory topology; original v4 validation passed. Migration selected `general`; v5 validation returned `MANAGED_READY` without errors or warnings. Same-plan replay changed no paths. Original hashes remained unchanged. |
| Small Stepwise v3 research project | 17 files, one existing Memory entry, three Results registrations and one legacy canonical registration. Original validation passed. Migration selected `research`; v5 validation returned `MANAGED_READY`, with three explicit legacy-output warnings. Only `project.md` changed among existing files; Memory, Results and original source hashes remained unchanged. Same-plan replay changed no paths. |
| Large Stepwise v4 research project | An APFS clone copied 29,996 ordinary files and preserved ten existing links, without hard links or a fallback that physically copies its 1.15 TB logical data. Runtime libraries and Git internals were excluded. Migration preserved ten questions' definition/version/message/event fields, one group's original fields, 29 Memory entries, 94 Results registrations and 29 canonical rows. One existing Attention became an investigation with its original content. Same-plan replay changed no paths. |

The large copy exposed a migration defect: historical links under Data stopped inventory even though migration neither reads nor changes their targets. The planner now reports `legacy_data_link_requires_review` without following those links. Managed inputs such as Memory still reject links. Four native-layout/version fixtures verify that an external target is never read or modified.

The large copy is **not a clean project-validation pass**. Before migration, its original governor reported one unfinished module-audit template. After migration, v5 reported 92 issues: 87 duplicate execution-number reports, three numbering reports, one repeated canonical-owner mapping and one preserved unresolved Attention blocker. These artifacts were retained, not silently repaired. The migration report also lists legacy outputs, definitions, Data provenance, experiments and unassigned files. This verifies preservation and reporting; resolving that project's scientific or maintenance work is outside product testing.

The original large project's 383 protected source/control/output files retained their hashes during this check. Two transient files in an independently running analysis changed or disappeared; no original project write was performed by the migration task. The copy is an isolated filesystem copy, not a coordinated snapshot of that ongoing analysis and not evidence for its analytical results.

Local manifests, exact plans, before/after validation, integrity comparisons and replay reports are under `/private/tmp/oppencouncil-real-migration-20261014/`. The large clone is `<temporary-acceptance-root>/research-v4`. Neither real project data nor copied governance records are product source or committed test fixtures. Configured production services were not registered against these copies; capability probes used a separate local site directory and no MCP connection.

The later shared-F owner correction removed one false duplicate-authority error: multiple legacy topic aliases may refer to the same F. Duplicate topic keys and duplicate non-F owners remain errors. The correction passed 19 tests on macOS, Windows and Linux. The saved immediate post-fix validation was blocked by lock-file permissions, so the previously stated 91-error total was an expectation, not a completed observation.

The subsequent human instruction restores acceptance of shared script numbers, both within a directory and across subdirectories. The new uniqueness restriction has been removed; the two-digit prefix requirement remains. Local project-check, script-operation, migration and output tests passed (142 tests), including shared numbers in both layouts and directory relocation without renumbering. A completed validation of the same isolated large copy now reports **four errors**: three missing prefixes (`R/operations/formal_control.py`, `R/reporting/refresh_current_delivery.R`, `R/reporting/verify_kidney_publication.R`) and the preserved unresolved investigation. None of the 87 former duplicate-number errors remains. The exact result is saved as `research-v4-shared-script-numbers.json` in the temporary report directory above. No scientific scripts were renamed or reordered. This remains a non-clean validation result, with legacy warnings and unassigned files still reported.

A final read-only comparison against the original protected-source manifest found 381 of 383 hashes unchanged; `project.md` and `R/operations/38_interaction_control.py` had changed since the earlier migration check. This task did not write either original file. The earlier migration-time equality remains its own observation; the final state is not reported as wholly unchanged. `source-final-check.json` preserves this distinction. No live source was reset to the earlier snapshot.

After the shared-number validation, the human explicitly requested deletion of the temporary large-copy directory because its volume was nearly full. `<temporary-acceptance-root>` was deleted without following its symbolic links. The original research project, development worktree and temporary validation reports remain. `temporary-clone-cleanup.json` records successful removal and observed free space; APFS shared blocks mean the copy's approximately 1 TiB `du` size was not its independently reclaimable size. No archive was created. The results above are retained observations, not a claim that the large copy remains available for another run.
