# Workbench UI maintenance notes

Read only when changing or testing the application UI. These are interface requirements, not instructions for writing research definitions.

## Reference and scope

The accepted visual reference is the user-supplied `oppencouncil-demo.html`. Retain its compact toolbar, issue navigation, comparison matrix, document treatment and separate discussion sidebar; the current palette and white wording surfaces follow the later user refinement below. Its synthetic content and simulated AI replies are not application behavior. The project directory/entry page is outside this redesign. Keep the existing storage schema, routes, version authority, request receipts and permission configuration.

The webpage supports reading options, discussing, editing candidate wording and explicitly confirming formal versions. The user manually invokes AI to continue. AI manages question grouping and dependencies through CLI/MCP. Do not expose group creation/membership forms, example/simulation panels, iframes, scale controls or automatic drafting/replies. Legacy example files remain recoverable in storage but are not fetched or rendered.

## Layout and visual hierarchy

Use one compact white top bar with the approved multicolor ring/checkmark logo, project/round, navigation toggle, synchronization status, refresh, save-all and a “复制交接说明” action that opens the manual handoff text for copying. Put visible search, two-by-two count filters, optional domain/status filters and issue navigation in the left sidebar. Keep the sidebar itself scrollable independently of the work area. List each grouped question only inside its group’s expandable member list, never again in the flat list. Search/status filtering must include matching members through their group; grouping does not change total question counts. Counts can overlap: a revised question may have a pending candidate and an effective version.

The center contains question/group context, an actual-record-derived three-step indicator (discussion, candidate review, confirmation), complete option comparison when present, then candidate/formal documents. The right sidebar contains discussion history and an always-available composer. Fix the desktop top bar and discussion header/composer while their content areas scroll. Preserve reading positions during same-item refresh/save; reset on navigation and reveal newly saved messages.

Use the project directory's light workspace and white toolbar, with violet actions and separate blue, amber, pink and green status accents. Separate the toolbar with a thin neutral line; do not add a colored ribbon along the toolbar or discussion header. Keep a clearly labeled '← 项目选择' link visible in the toolbar on all screen sizes. Options use distinct orange, purple, blue and green accents. Candidate, effective and historical wording use plain white reading surfaces. Effective wording retains a green confirmation seal and Chinese serif body typography. These states must come from stored records; a preference or candidate save never earns an effective seal. Body text and line breaks remain exact, selectable and untruncated.

Use a coherent type scale: 28px topic heading (24px on phones), 21px section heading, 19px document/option heading, 15px ordinary body, 14px comparison/discussion and 12–13px metadata. Effective document text is 16.5px with 1.95 line height; candidate text is 15px with 1.9 line height, medium weight (500) and deep ink (#252c38). Candidate code and quotations inherit this weight and color; the unsaved Markdown preview uses the same reading treatment. Use local font stacks with PingFang/system sans-serif for UI and Songti/STSong/SimSun for formal Chinese. No network font dependency is required. Keep the actor on the left with a compact avatar and time on the right; discussion body aligns beneath the actor name. Separate discussion messages with space, not document frames.

The approved logo source is `council/oppencouncil/assets/logo.svg`, supplied as `oppencouncil-mark.svg`. Keep its original colors and square viewBox in the project directory, access page and workbench; inline copies are presentation assets and must match this source.

### Responsive behavior

- Desktop: the main work area and right discussion sidebar fill the available viewport height. Center content scrolls naturally from comparison to wording. Drag the discussion sidebar’s left divider to resize it between 300px and 55% of the detail area. Keep the main content usable, reflow comparison cards as needed, and retain the desired pixel width in site-local browser preferences across questions, groups and reloads. Double-click or Enter restores the responsive default; arrow keys adjust width (Shift for larger steps), Home/End reach the bounds, and Escape cancels an active drag. Resizing never saves project data or alters pending edits. Below 1024px, hide the divider and use the full-width stacked discussion; returning to desktop restores the preference within current bounds.
- When the center itself reaches 1520 CSS pixels, place comparison and wording side by side with independent scrolling. Keep context above them, using the extra header width for the progress indicator. Without options, retain one document region.
- When the center is at most 760px wide, stack complete options vertically and repeat each rule/impact label inside its card. Compare at most two options at a time; never drop rules or truncate text within a shown option. Leave inset clearance around the scrollable comparison matrix so rounded borders and keyboard focus outlines are not clipped.
- Below 1280px viewport width, turn navigation into a drawer, opened with the toolbar toggle and closed by selection, backdrop, close button or Escape. `/` focuses search. Toggling navigation does not discard drafts or issue selection.
- Below 1024px, put center content and discussion in natural vertical flow with a sticky compact toolbar. Below 640px use 16px horizontal workspace padding and 16px editable text to keep phone inputs usable. Avoid page-level horizontal overflow.

### Comparison and formal documents

Compare coupled approaches as option columns: label, concise decision-focused rules for every member, actual consequences and conditions/trade-offs. Independent dimensions and local values use inline choices within those rules or discussion; do not expand every combination into another column. Keep shared explanations together in the current discussion and full normative wording in the member candidates, avoiding repeated candidate documents in comparison cells. Initially show the first two options, including an already preferred option if it falls outside them. When there are more than two options, keep the full option list in a closed '选择比较方案' disclosure. Reviewers can uncheck a shown option and select another, retaining between one and two visible options. Preserve their display selection per group in tab session storage; reset it when option content changes. Keep original option IDs, letters and preference targets when columns are filtered. Display selection makes no project writes, does not create unsaved work, and does not exclude options from handoff. Clicking an option preference appends its wording to the editable shared discussion composer, preserves existing prose and makes no API write. Repeated clicks on the same option do not duplicate the line. Only explicit discussion save submits the message. Existing saved preference markers remain historical; a local click must not claim a saved preference. Do not invent missing explanation or imply that selecting an option confirms wording. Options and discussion remain visible together on desktop; no separate discussion/options mode is needed.

Every question retains its own full formal text, ID and version history. Show a pending candidate before the current/historical comparison; without a candidate, show the current version in full. Put V1/V2/etc. in a separate top-right badge, pending status explicitly beside candidate versions, and confirmation date at the bottom of effective/historical records. Keep ID, confirmer, source and history in closed details disclosures. Expanding details preserves the confirmation date at the bottom. Dependency warnings requiring action stay visible. Never place historical text ahead of the candidate or rewrite it for presentation.

Save candidate edits beside their editor, separately from confirmation. Disable empty/unchanged saves. Opening a revision keeps the current version effective. Both individual and joint revisions expose “取消修订” (or “撤回候选” before the first version). Cancellation archives saved candidates and unfinished local wording, returns to the effective display, and leaves discussion unchanged. Joint cancellation checks the reviewed group/member token and withdraws all candidates together. Matching archived local-edit receipts clear pending inputs, including after response loss and refresh.

Every pending candidate exposes “确认并冻结本条口径” beside its full wording, in both individual and grouped review. This confirms only that question and never submits other members. Group membership organizes review and discussion; it does not force simultaneous publication. The group footer separately offers an explicit optional “确认本组 N 条口径” batch action. Effective and historical versions remain records, with no duplicate confirmation action.

Individual confirmation checks only this question's unsaved wording/message and real prerequisite readiness. Other members and shared discussion drafts remain untouched and do not block an individual confirmation. A dependency on an unconfirmed prerequisite is visibly explained; confirm upstream first, or explicitly choose the separate batch action for a genuinely coupled cycle. Once an initially unbound prerequisite is confirmed, the refreshed candidate binds its exact visible version for approval; known stale bindings still need review. Optional joint confirmation commits the reviewed combination together. Only unsaved wording/messages on this group's members or this group's shared discussion can block that batch action; unrelated question/group drafts must remain untouched and must not disable it. All repeated buttons update together. Show an adjacent, accessible explanation for every local blocker (missing candidate IDs, member edits/messages or shared discussion), clearing it when saved or reverted. Busy requests disable duplicate submissions. Internal dependencies awaiting the same group transaction are not local blockers; server-side token, revision and dependency validation still apply. Independent confirmation likewise explains its own pending wording/message and ignores unrelated drafts. Member detail includes shared messages with their origin labeled and links to shared discussion/confirmation. New discussion from a member routes to the shared group composer; pre-existing unsaved individual messages remain recoverable. Recommendations and legacy human replies are discussion, never formal versions.

Show unresolved external prerequisites and changed upstream wording. Same-group prerequisites awaiting joint confirmation are not external blockers. Keep hashes, self-checks, tool logs and backend review notes out of the entire human webpage, including collapsed panels and handoff. Preserve meaningful sources and exact formal text. Historical AI display corrections retain originals; this operation cannot alter human messages or formal wording.

### Navigation and preparation

Each group and question has a distinct project URL (`?group=B-NNNNNN` or `?question=F-NNNNNN`). Initial URLs override session selection. Navigation uses browser history; Back/Forward restores the referenced item without clearing pending discussion or wording. Refresh/deep links stay on the same item; ordinary saves do not add history entries. Keep the project-selection link.

Do not label empty records as formal wording. Groups with a missing candidate/current member document show the affected IDs and a preparation notice. Prepared member candidates can still be individually confirmed when their own prerequisites are satisfied. Missing members block only the batch confirmation; no incomplete group can be batch-confirmed. Partial preparation remains the discussion stage. This presence check does not establish semantic completeness; skills must verify complete normative content before announcing review readiness.

### Motion

Use short (160–220ms) transitions for expandable details, history, filters, navigation, comparison changes, buttons, dialogs and notices. Animate opening and closing, allow rapid reversal, and release fixed heights after disclosure animation so long content remains readable. Keep hidden navigation inert and retain existing modal focus/keyboard behavior. Honor `prefers-reduced-motion` with immediate state changes. Native disclosure behavior remains available when animation APIs are absent.

### Inline parameter choices

Comparison rules, consequences, tradeoffs and discussion may contain `{{choice:retry_seconds;重试等待;5秒;10秒;30秒}}`. Render the extension as text with a dashed underline: a custom button shows its label before choosing and the selected value afterward. It opens the shared Council listbox popover, with no native select menu. The status filter uses the same component. Use no colored chip, enclosing box or permanent extra button. Place “添加到讨论” and “清除选择” in the parameter popover footer, enabled only for a selected value. Choosing a value keeps the popover open; adding to discussion explicitly appends the draft. Status choices apply the filter and close immediately. Preserve all earlier storage and confirmation semantics. A choice needs an ASCII stable ID, a label and 2–12 distinct nonempty values; semicolons separate fields without disrupting Markdown tables. Escaped notation, inline/fenced code, link labels and malformed notation remain text. Values are plain text, never executable HTML. Candidate, effective and historical documents do not activate interactive choices.

The shared popover uses the page palette, custom option/check states and short reduced-motion-aware transitions. Mount it outside scrolling reading containers; clamp width/height to the visible viewport and flip upward when needed. Arrow keys and Home/End move the active option without choosing; Enter/Space choose, Escape closes and returns focus, and Tab can reach the footer. Outside clicks, navigation, parent scrolling or resize dismiss it; internal list scrolling stays open. Keep ARIA listbox/option state, focus return and touch targets usable. Search uses the page’s own clear button. App-authored dropdowns and action popups must not use browser/OS select, alert or prompt dialogs.

Remember each selected value locally by project, question/group and parameter ID. A changed label/value set invalidates the old selection. The placeholder is not a default choice; selecting or clearing an option makes no API write and does not mark formal text confirmed. Repeated occurrences of the same parameter in one topic stay synchronized. If browser storage fails, retain the in-memory preference and tell the person how to save it through discussion.

“添加到讨论” appends a labeled parameter preference to the active question or shared discussion draft and opens its composer. Preserve existing prose and add punctuation between successive snippets. Never submit, confirm or rewrite candidates on selection or append. The reviewer can edit, then save normally or with the discussion shortcut. Existing source Markdown remains unchanged. Both skills require semantic segmentation within each F question. Independent subchoices and local numeric variations use this extension; coupled approaches use separate columns. AI explains consequences and checks affected rules after saved discussion. The full authoring workflow belongs in the skills, while this document specifies rendering and interaction.

Add the selected plain text as an escaped Markdown blockquote, with its question/group ID and option/version/author context. Preserve paragraph breaks and existing discussion drafts; put the caret after the quote for a reply. Quoting from a group member routes into shared discussion while retaining any earlier individual draft. Support multiple quotations, refresh recovery, the normal save button and Cmd/Ctrl+Enter. Selecting, quoting or changing inline values never sends a message or changes formal wording. Only explicit save persists the discussion.

Restrict quotations to one source block, excluding editors, unsaved previews and interface controls. Keep the action within the viewport and dismiss on selection collapse, scroll, navigation or Escape. Escape Markdown metacharacters so quoted code, HTML and choice notation stay inert. A quote captures the selected text and source label at that time; it does not track later edits or replace the formal source.

Do this for discussion, comparisons, definitions and previews, leaving stored source unchanged. Do not link unknown IDs, code, file paths or text already inside a link. Open these references in a new browser tab with `target="_blank"` and `rel="noopener noreferrer"`; leave the current page's selection, reading position, drafts and history intact. Sidebar navigation continues to switch questions within the current page. Both skills and the handoff prompt ask AI to use the original uppercase F, ASCII hyphen and six-digit ID in prose.

Support double-asterisk bold immediately beside Chinese punctuation, including `**建议：**正文` and `**（建议）**正文`, through Markdown delimiter parsing. Preserve escaping, code, nested inline formatting and the existing HTML/link safety rules.

In both individual and shared discussion composers, Cmd+Enter on macOS or Ctrl+Enter on Windows/Linux invokes the same save action as the button. Show the platform shortcut by the save control; accept either modifier so embedded browsers with a different reported platform remain usable. Plain Enter inserts a newline; candidate editors are unaffected. Ignore composition/IME confirmation, repeated keydown, empty input and saves already in progress. Preserve the existing success, failure and recovery feedback.

Render candidate, effective and historical wording through the same local Markdown renderer in both individual and joint review. Support headings, emphasis, ordered/unordered nested lists, links, blockquotes, tables, horizontal rules, inline code and fenced code. Preserve soft line breaks for existing prose. Keep typography replacements disabled so punctuation is not rewritten. The stored Markdown source remains the sole authority: editors, saved versions and handoff retain it; rendered HTML is presentation only and is never written back to the question record.

Existing save/approval separation, conflict checks, receipts, cancellation and history rules still apply. Table and code overflow scroll inside the document, not the page.

Render comparison options' member rules, actual consequences and tradeoffs through this same Markdown renderer. Apply the shared heading, list, table, quotation and code styles inside each comparison cell, including stacked phone cards; wide tables and code scroll within their cell. Keep compact option labels and row metadata as plain text. Preserve every option's exact Markdown source in storage and handoff; changing comparison visibility or rendering never writes a preference or confirms wording.

Bundle the pinned `markdown-it` browser distribution locally with its license and provenance. Do not execute embedded HTML, scripts or code blocks. Render both individual and shared discussion bodies with this same safe Markdown renderer, including AI proposals, human replies and earlier discussion displays. Keep author/time metadata separate, scale headings to the discussion typography, and scroll wide tables/code inside the message. ## Drafts, saves and handoff

Cache pending inputs synchronously in project-keyed, tab-specific sessionStorage. Show per-question/group unsaved markers and a footer count. Request the browser leave warning while pending changes exist. Report failed caching visibly. Closing a tab is not durable storage; AI/MCP reads explicitly saved records only. Navigation/search/status filters affect the visible list, never the complete save/handoff scope. Retain selection and filters across reloads in the same project tab.

Retain each candidate edit's original text/version for conflict comparison. A conflicting refresh preserves the local edit and requires an explicit choice before overwriting project wording. Save sequentially under revision checks; partial failure identifies remaining unsaved items. Use stable request IDs for uncertain retries. Reconcile discussion only by request ID, user actor and exact text. If another edit arrives during a save, clear only the sent input.

Show one dismissible notification near the bottom safe area. Success fades; errors remain until dismissed/replaced. Keep synchronization state in the top bar and pending counts in the footer. Saving discussion clears the sent input while leaving the composer available. Network/session failures instruct the reviewer to restore the service/forwarding and use “刷新项目记录”, preserving drafts. Never show success based only on a button click.

Handoff lists every pending question/group. Offer save-all or explicit exclusion of unsaved items, with excluded IDs named in the summary. Include saved discussion even for unanswered questions. The prompt asks for all currently identifiable decisions with concrete actions/consequences and directs AI to organize complete human decision topics. AI must examine unresolved cross-topic prerequisites, include rules needed to compare the same scenario (including one-way dependencies), prepare independently decidable upstream topics first, and check for cycles between topics. Candidate presence alone does not establish that a topic is complete enough to review. Preserve real dependency bindings and exact per-question authority. Handoff does not invoke AI. The modal traps focus, closes with Escape, returns focus and reports copy success/fallback selection.

### Password entry and session controls

Default sites show a custom first-run password form before exposing the project directory or project data. After setup, the same page becomes a password-only login form; no username is collected. Use the Council palette, local logo, labeled password/repeat-password fields, a custom visibility toggle and inline validation/progress/error states. Keep native form submission and validation popups disabled in favor of these page controls. Preserve the requested path and query when returning from login, including question/group links. Passwords never enter draft storage, URLs or console output.

Show a compact Exit control in the directory and workbench for password-protected sites. Workbench Exit asks the reviewer to save pending work before leaving. A 401 shows a new-tab login link, leaves local drafts and the reading context intact, and permits refresh after reauthentication. The backend password/session contract is owned by the Council README's 站点密码 section.
